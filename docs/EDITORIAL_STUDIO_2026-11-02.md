# Events, Marathi Studio, source evidence, updates and readiness

Six requested newsroom features are available in the existing Admin Room. The phone PostgreSQL database remains authoritative; public delivery continues through the existing reviewed GitHub outbox. The main owner remains pushkarthawari. Existing Verify continues to publish directly with no additional evidence prompts or confirmation dialogs.

1. Events & sources searches the accessible database by source/headline/text and shows the newest 100 matching source records with the full match count. Editors select up to ten reports per grouping action, create durable event groups, append subsequent source reports and compare original attributions/excerpts/times. The newest 50 confirmed groups and lexical suggestions among 200 matching records are shown. Suggestions are labelled candidates and require editor grouping, especially across languages.
2. Marathi Studio opens a real story, preserves its original source headline/text before rewriting, offers source headline options, extracted names/numbers, source-reported timeline, editable draft/context, image rights, and escaped mobile preview. Source outlines preserve quoted source language and are never passed off as machine translation. Automatic Marathi drafting uses the existing configured newsroom model, validates output and rejects newly introduced numeric tokens. Slow inference runs in a bounded background job queue with persistent results/status and an interrupted-job state. The model must actually be configured and running on the phone; its absence is explicit and manual editing/source outlines remain available. Generated copy needs editor review and is never automatically saved, approved or published.
3. Claims hold specific assertions, editor-supplied HTTPS evidence excerpts, publisher groups, evidence stance and the editor assessment. Evidence is attributed to the person recording it. Changes to the reviewed copy cause old assessments to display a review-needed state through content fingerprints; storing evidence does not establish independent fact-checking or originality.
4. Breaking updates and corrections are durable proposals. Confirmed-event reports and lexical follow-up candidates can populate a proposal; these retain the original source and require review. Only staff with publishing permission can publish updates. Row locking/SQLite immediate transactions, a base-content fingerprint and a published-state guard prevent duplicate appends and stale overwrites. The public body contains the update/correction label, IST timestamp and source; the original publication date stays intact. Updated articles enter the existing durable public-delivery queue. Reader acceptance checks verify the published correction on the actual article route. Existing advertising review proof is invalidated by changed copy.
5. Main-owner staff controls now include exact permissions, allowed desks and assigned-stories-only access. Primary-owner powers cannot be delegated or removed. Staff policies are checked on each freshly authenticated request. Queue rows, totals, source coverage, studio reads, direct story writes and source selections obey the same restrictions. Operational/report/settings powers require an unrestricted scope to prevent cross-desk information leaks. Changing a role restores that role's defaults and removes custom restrictions. Main owner can assign stories in the studio; manually created drafts are owned by their creator. Staff credentials remain hashed and preserved.
6. AdSense readiness displays all-published database counts and paginated article findings based on existing local search/advertising rules, alongside actual ads.txt/policy-file checks. An explicit HTTP check fetches the fixed public site URLs with bounded concurrency/timeouts; a failed server fetch is not represented as Google's crawler status. The panel links to official guidance and does not claim approval, a Google word-count requirement or proof of originality from an automated check.

New source evidence, event groups, claim assessments and updates are included in the live diagnostic PDF. HTTPS bridge routes remain explicitly allowlisted. New schema is additive and created on authorized setup/write paths; dashboard/source reads do not generate fake activity, approvals or agent runs. New editorial data is cleared from browser memory/DOM on logout. Navigation scrolls on smaller screens so account controls remain reachable.

Validation: 405 Python tests with real local PostgreSQL 18, 52 JS tests, 23 reader browser checks, 22 existing admin checks and 10 new editorial acceptance checks. Tests include multi-source grouping, original-source preservation, stale evidence, direct publication, visible reader correction history, restricted staff browser/API access, persisted PostgreSQL policies and updates, async job completion/failure/interruption, exact bridge scoping and actual response-based HTTP diagnostics. Synthetic fixtures alone were published during acceptance testing; production articles and staff were not mutated.

Deployment publishes the new interface/gateway. Run the existing immutable backup-preserving Termux updater for the merged revision, then sign in again to activate the phone-side endpoints and policy enforcement. Existing users/passwords and source data are retained. Automatic model generation remains dependent on the user's configured local inference service.
